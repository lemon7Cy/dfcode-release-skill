The earlier 0.2.26 live signing/notarization run supplies workflow experience; it does not by itself prove every new generic branch of the skill end-to-end.

## Windows Native Extension — 2026-09-12

Version 1.1.0 adds Windows x64 input verification, KeyLocker SMCTL `--simple` signing, Engine manifest/updater refresh, NSIS installer and uninstaller signing hooks, final extracted-payload verification, final-byte metadata/Full OTA ZIP creation, interruption journals and GitHub publication evidence checks. Direct `windows-release.cjs --execute` remains handoff-only; actual signing requires `--sign --execute`, also supplied by the shared native sign command.

- Final Windows test run: **127 tests, 124 passed, 0 failed, 3 explicitly skipped** because native symlink creation lacked Windows privileges (EPERM). The skipped cases concern Mac framework symlink traversal and output symlink protection. Skill frontmatter validation and `git diff --check` passed.
- Deterministic tests cover default read-only mode and host routing, public certificate config rejection, source/hash/archive checks, exact certificate/publisher/timestamp verification, approved Microsoft signature preservation, detached signing and unresolved-outcome recovery, hook failures, NSIS scope preservation, manifest refresh, blockmap consistency, state/config/notes binding, final report validation and publication aliases. Signing/build/provider operations are mocked in those tests.
- Existing historical 0.2.26 artifacts were replayed locally through the new input and packaging modules without a new signature or production build. The full input ZIP passed 122 internal checksums, BUILD-INFO/receipt/source validation, its 12-entry PE inventory and original unsigned OTA metadata checks. The 102-file application payload passed Engine/skills, 419 ASAR file hashes, embedded integrity and fuse parsing. A replay-only receipt used saved historical GitHub run/asset evidence; no fresh CI collection was claimed.
- The final historical NSIS was extracted by the pinned toolset and matched the retained signed payload exactly. Unsigned-to-signed comparison accepted only signature data and the intended Engine/updater metadata changes. The new embedded-uninstaller extractor matched the retained signed uninstaller's exact bytes (236,504 bytes; SHA-256 `e0786e48522bb49cd802e0ffa3c8514fec6193535b5a17ad3bc13696dd945ec8`).
- The packaging-config converter was replayed against the actual historical source settings: `oneClick=false`, directory selection enabled, `perMachine=false`, `allowElevation=false`. This confirms those settings were preserved; it is not an all-users installation fix or installation test.
- The new signature verifier actually revalidated 13 historical PEs: 11 company-signed and 2 preserved Microsoft DLLs, using Authenticode and SignTool trust/timestamp checks. Those signatures were created during the earlier release, not this implementation. The new signer explicitly preserves only approved valid Microsoft signatures for the two supported DLL names.
- Final-byte metadata creation was executed against the historical signed EXE: blockmap, feed, schema-v3 manifest and the four-root-file Full OTA ZIP were regenerated and independently checked. The original installer stayed unchanged. The replay used a clean detached Studio source pin with Node 22.22.3, Bun 1.3.14, Electron 37.10.3 and builder/lib 26.15.3; no old dependency directory was copied into that checkout.
- This extension work performed deterministic tests and historical replays only. No fresh real signing request, Windows install/launch/uninstall, real OTA, production build, Admin upload or publication was performed as part of implementation. Historical signing evidence does not prove every generic branch end-to-end.
